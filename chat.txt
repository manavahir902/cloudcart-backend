Phase 1: AWS Account & IAM
Why this phase exists
Your AWS root account is like the master key to your house — it can delete everything, see billing, change security settings, nothing can stop it. If that key leaks (committed to GitHub by accident, phished, etc.), you lose everything, possibly with a huge bill attached. So the very first rule of real AWS work: you never use the root account for daily work. Instead, you create a limited "IAM user" (Identity and Access Management) for yourself, and lock the root account away.

This is also the #1 thing interviewers ask about — "how do you secure AWS access" — and "I use IAM users/roles, never root" is the correct answer.

Step 1.1 — Secure the root account
Log into AWS Console → search IAM → top right, click your account name → Security credentials.
Under Multi-factor authentication (MFA), click Assign MFA device.
Use an authenticator app (Google Authenticator / Authy) — scan the QR code, enter the 2 codes it asks for.

Why: Even if your root password leaks, nobody can log in without your phone. This alone stops 90% of AWS account hijacks (a very common horror story in beginner AWS forums — people waking up to $50k bills from crypto-mining because their root creds leaked).

Phase 2: Custom VPC
Why this phase exists

By default, every AWS account gives you a "default VPC" already set up — and beginners just launch EC2 into it and never think about networking. That's exactly why this project has you build one from scratch: networking is the #1 thing that separates people who can click around AWS from people who actually understand cloud infrastructure.

A VPC (Virtual Private Cloud) is your own private, isolated network inside AWS — like having your own building instead of renting a desk in a shared office. Nothing enters or leaves it unless you explicitly allow it. Everything else we build (EC2, RDS, Load Balancers) will live inside this network, in specific rooms (subnets) with specific doors (route tables, gateways) that we control.

Step 2.1 — The IP range (CIDR block)

We're using 10.0.0.0/16 as decided in the disc. Let's understand what that actually means, because you'll be reading /24, /16 etc constantly in AWS.

10.0.0.0 — a private IP range reserved for internal networks (never routable on the public internet — that's why it's "private")
/16 — means the first 16 bits are fixed (10.0), and the remaining 16 bits (65,536 addresses) are yours to divide up

Think of /16 as: "I own the entire 10.0.x.x neighborhood." We'll then carve out smaller streets (/24 subnets = 256 addresses each) for specific purposes — public web servers, private app servers, private databases.

Why not just use one big flat network? Because segmentation = security. If your database subnet has no path to the internet at all, no attacker can reach it directly even if they somehow get in through your app. This is called defense in depth.

Step 2.4 — Create the Route Table for public traffic

A Route Table is literally a list of rules: "if traffic is going to X destination, send it out door Y." Right now, AWS gives your VPC one default route table that only knows how to route within the VPC (local traffic). We need to add a rule: "anything going to the internet (0.0.0.0/0) → go out through the Internet Gateway."

Console → VPC → Route Tables → Create route table

Name: cloudcart-public-rt
VPC: cloudcart-vpc
Create → select it → Routes tab → Edit routes → Add route
Destination: 0.0.0.0/0
Target: your Internet Gateway (cloudcart-igw)

CLI:

bash
aws ec2 create-route-table \
  --vpc-id vpc-xxxxxxxx \
  --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=cloudcart-public-rt}]'

aws ec2 create-route \
  --route-table-id rtb-xxxxxxxx \
  --destination-cidr-block 0.0.0.0/0 \
  --gateway-id igw-xxxxxxxx

We will later create a separate route table for private subnets (Phase 4, using NAT Gateway instead of IGW) — that's what makes the difference between "public" and "private" subnets. It's not a setting on the subnet itself — it's entirely about which route table it's associated with. This is a core AWS concept that a lot of people misunderstand, so make sure this clicks: a subnet is "public" simply because its route table sends 0.0.0.0/0 traffic to an Internet Gateway. Nothing more, nothing less.

Phase 3: Public & Private Subnets
Why this phase exists

A VPC alone is just an empty network — you can't launch anything directly into it. You have to divide it into subnets (sub-networks), and every subnet must belong to exactly one Availability Zone (AZ).

What's an Availability Zone, and why do we use two?

An AZ is essentially a physically separate data center (with its own power, cooling, network) within a region. AWS Mumbai (ap-south-1) has multiple AZs — e.g. ap-south-1a, ap-south-1b.

Why does this matter? If your entire app lives in one AZ and that data center has a power outage or hardware failure (rare, but it happens — AWS has had real outages), your site goes down completely. By spreading resources across 2 AZs, if one fails, the other keeps serving traffic. This is the literal definition of High Availability (HA) — it's not a buzzword, it's "don't put all your servers in one building."

This is also a very common interview question: "How would you design for high availability?" → Answer: "Multi-AZ deployment with redundant resources in each tier."

The 6 subnets we're building
Subnet	CIDR	AZ	Purpose
Public A	10.0.1.0/24	ap-south-1a	ALB, NAT Gateway
Public B	10.0.2.0/24	ap-south-1b	ALB

Private DB A	10.0.21.0/24	ap-south-1a	RDS
Private DB B	10.0.22.0/24	ap-south-1b	RDS

Why "private" for app and DB servers, not just DB? A common beginner mistake is putting the app server in a public subnet "because it needs to serve traffic." It doesn't — the Load Balancer sits in the public subnet and takes the internet traffic, then forwards it privately to your EC2 instances. Your app servers never need a direct public IP. This means even if someone scans the internet for open ports, they can't reach your app server directly — only through the ALB, which we control tightly. Same logic, even stronger, for the database: it should never be reachable from the internet, period.

Phase 4: NAT Gateway & Security Groups
Why this phase exists

Your private app subnets (private-app-a, private-app-b) currently have zero route to the internet — not even outbound. That's a problem: when you SSH into your EC2 instance later and run npm install, or your app needs to call an external payment API, it needs outbound internet access. But we absolutely do NOT want it to have inbound internet access (nobody should be able to reach it directly from outside).

This is exactly what a NAT Gateway solves: it's a one-way door. Traffic can go out to the internet, responses can come back, but nobody outside can initiate a connection in. Think of it like calling someone from a private number — you can call out, but they can't call you back directly.

Step 4.1 — Allocate an Elastic IP for the NAT Gateway

A NAT Gateway needs a fixed public IP to operate from.

cmd

Copy the AllocationId from the output (looks like eipalloc-xxxxxxxx).

Important: A NAT Gateway must live in a public subnet (it needs the IGW route to actually reach the internet), even though it's serving private subnets.

cmd

Step 4.4 — Security Groups (the real firewall)
Security Groups vs NACLs — the concept, before we build
Security Group (SG): Attached to a resource (EC2, RDS, ALB). Stateful — if you allow inbound traffic, the response is automatically allowed out, you don't need a separate outbound rule for replies. This is your primary, everyday firewall.
NACL (Network ACL): Attached to a subnet, not a resource. Stateless — inbound and outbound rules are evaluated independently. Used for broader, coarser rules (e.g., "block this specific malicious IP from the entire subnet"). We'll set these up in Phase 21 alongside WAF; for now, default NACL (allow all within VPC) is fine.

Why both exist: SGs are for "who can talk to whom" at the resource level (fine-grained, allow-only). NACLs are a blunter, subnet-wide backstop (can explicitly deny). Real production setups use SGs as the main defense and NACLs as an extra layer — this is "defense in depth" again, same principle as public/private subnets.

The 3 security groups we need

Your traffic flow is: Internet → ALB → EC2 (App) → RDS (DB). Each tier should only accept traffic from the tier directly before it — nothing more.

1. ALB Security Group — accepts traffic from the whole internet on 80/443 (that's its job, it's the public entry point):

cmd
aws ec2 create-security-group --group-name cloudcart-alb-sg --description "ALB - public facing" --vpc-id vpc-0bc58919ca1388727

Copy the GroupId, then add rules:

cmd
aws ec2 authorize-security-group-ingress --group-id <alb-sg-id> --protocol tcp --port 80 --cidr 0.0.0.0/0

aws ec2 authorize-security-group-ingress --group-id <alb-sg-id> --protocol tcp --port 443 --cidr 0.0.0.0/0

2. App (EC2) Security Group — accepts traffic ONLY from the ALB security group, not from the internet directly. This is the key insight: SG rules can reference other SGs as the source, not just IP ranges — that's how we say "only my load balancer can talk to my app servers":

cmd
aws ec2 create-security-group --group-name cloudcart-app-sg --description "App servers - internal only" --vpc-id vpc-0bc58919ca1388727

aws ec2 authorize-security-group-ingress --group-id <app-sg-id> --protocol tcp --port 3000 --source-group <alb-sg-id>

(Port 3000 = standard Node/Express default port — we'll confirm this matches your app in Phase 6.)

We'll also temporarily allow SSH (port 22) so you can connect and set up the server — but only from your own IP, never 0.0.0.0/0:

cmd
aws ec2 authorize-security-group-ingress --group-id <app-sg-id> --protocol tcp --port 22 --cidr <your-ip>/32

To get your current public IP: search "what is my ip" in your browser, then use it like 49.36.xx.xx/32.

Why not just allow SSH from anywhere? Port 22 open to 0.0.0.0/0 is one of the most commonly scanned/attacked ports on the entire internet — bots constantly probe for it. Restricting to your IP closes that off almost entirely. (In Phase 5 we'll actually discuss replacing this with Systems Manager Session Manager, which needs no open SSH port at all — the real production-grade approach.)

3. Database Security Group — accepts traffic ONLY from the App security group, on MySQL's port:

cmd
aws ec2 create-security-group --group-name cloudcart-db-sg --description "RDS - app access only" --vpc-id vpc-0bc58919ca1388727

aws ec2 authorize-security-group-ingress --group-id <db-sg-id> --protocol tcp --port 3306 --source-group <app-sg-id>

Now trace the chain: Internet → only 80/443 → ALB-SG. ALB → only 3000 → App-SG. App → only 3306 → DB-SG. Nothing skips a tier. This is the actual architecture from the disc's diagram, now enforced at the firewall level — not just drawn on paper.

Phase 6: Web Application Deployment
Why this phase exists

We now have a running server, but nothing on it. This phase does three things: build a real Express backend, get it onto the server, and put Nginx in front of it. Let's understand the Nginx part before we build it, since it's the piece beginners usually skip and don't understand:

Why Nginx in front of Node, instead of exposing Node directly?

Node/Express apps typically run on port 3000. Nginx sits on port 80 and forwards ("reverse proxies") requests to Node behind the scenes.
Nginx is far better at things Node isn't optimized for: serving static files (product images, CSS/JS bundles) efficiently, handling many simultaneous slow connections, SSL termination later, and basic rate limiting/security headers.
It also means if you later run multiple Node processes (PM2 cluster mode) or even multiple servers, Nginx/ALB can distribute traffic — Node itself was never meant to be the internet-facing edge.

This app-behind-a-proxy pattern is standard in virtually every production Node deployment — not just AWS-specific.

Phase 7: Application Load Balancer (ALB)
Why this phase exists

Your server works, but it's unreachable from the internet — by design, it's in a private subnet. The ALB is the piece that sits in your public subnets, gets a public-facing address, and forwards traffic to your private EC2 instance(s). This is also the moment your architecture becomes "highly available" in practice, not just on paper — the ALB continuously health-checks your instances and only sends traffic to ones that are actually healthy.

Why not just give the EC2 instance a public IP directly, skip the ALB? A few real reasons:

Health checks — if your app crashes, an ALB stops sending it traffic automatically. A direct public IP has no such safety net.
Multiple instances — later (Phase 8, Auto Scaling), you'll have 2+ EC2 instances. The ALB is what distributes traffic across them — a single IP can't do that.
SSL termination — the ALB will handle HTTPS (Phase 15) centrally, so your app code never has to deal with certificates.
One stable entry point — EC2 IPs can change (e.g., on restart); the ALB gives you one permanent DNS name regardless of what's happening behind it.

Phase 8: Auto Scaling Group (ASG)
Why this phase exists

Right now you have exactly one EC2 instance. Two real problems with that:

No redundancy — if that single instance crashes, or its AZ has an outage, your site goes down completely. The ALB can only route to healthy targets; it can't create new ones.
No elasticity — if traffic spikes (say, a sale event), one t2.micro will choke. You'd have to manually notice and launch more servers.

An Auto Scaling Group solves both: it maintains a desired number of healthy instances, automatically replaces any that fail health checks, and can scale the count up/down based on load — all without you intervening.

Key concept: Launch Template. Instead of manually clicking through "Launch instance" every time (like we did in Phase 5), we define a template — AMI, instance type, security group, IAM role, user data script — once. The ASG then uses that template to launch identical instances automatically, wherever and whenever needed.

Phase 9: Amazon RDS (MySQL Database)
Why this phase exists

Right now your data (products, users) lives in memory inside the Node process — meaning every time PM2 restarts the app, or the ASG replaces an instance, all data is wiped. That's obviously unworkable for a real e-commerce app. RDS gives you a managed, persistent, durable MySQL database that lives independently of your app servers.

Why "managed" matters, and why not just install MySQL on an EC2 instance yourself: RDS handles automated backups, patching, failover (Multi-AZ), and monitoring for you. Running your own MySQL on EC2 means you're responsible for all of that — backup scripts, patching schedules, replication setup. For a resume/interview project, using RDS correctly (with Multi-AZ, backups, private subnets) is the actual signal of production-readiness; self-managed DB-on-EC2 is generally what beginners do and companies specifically try to avoid.

Phase 11: Amazon S3 (Image Storage)
Why this phase exists

Product images and user profile pictures shouldn't be stored on your EC2 instances. Two reasons: (1) EC2 instances in your ASG are ephemeral — they get replaced/terminated (you saw this yourself in Phase 8), so anything stored on local disk vanishes with the instance; (2) even if they didn't, serving images through your Node app is slow and wastes compute that should be handling API logic. S3 is built specifically for storing and serving files at scale, cheaply, and durably (99.999999999% durability — "11 nines").

The upload pattern we're using: pre-signed URLs. A common beginner mistake is routing the actual image bytes through your Express server (multer uploads → then push to S3). That works but doubles bandwidth (client→server→S3) and loads your API server with file traffic it doesn't need to handle. The production pattern: your backend generates a temporary, permission-scoped URL, and the client uploads directly to S3 using that URL. Your server never touches the image bytes at all.

Step 11.1 — Create the S3 bucket

Console → S3 → Create bucket

Bucket name: cloudcart-pro-images-<something-unique> (S3 bucket names are globally unique across ALL AWS accounts worldwide, so add your name/random numbers, e.g. cloudcart-pro-images-manav2026)
Region: ap-south-1 (same region as everything else — keeps latency low and avoids cross-region data transfer costs)
Object Ownership: ACLs disabled (recommended) — bucket owner enforced
Block Public Access settings: Keep all 4 boxes checked (block all public access) ✅ Why block public access on an image bucket, if we want people to see product images? This is the key insight: we don't make the bucket public. We'll instead serve images through CloudFront (Phase 17), which can access the bucket privately on the backend while still serving images publicly through its own URL. This is significantly more secure than a public S3 bucket, and also faster (CDN caching) and cheaper (CloudFront pricing vs raw S3 data transfer). Punching a hole in "block public access" is one of the most common real-world AWS misconfigurations that leads to data leaks — so we build the correct habit from the start even though it means images won't be viewable via direct bucket URL yet.
Enable Bucket Versioning: keep disabled for now (adds cost/complexity; fine to enable later if you want undo-history for images)

Phase 12: Amazon Cognito (Real Authentication)
Why this phase exists

Our hand-rolled JWT auth (Phase 6/10) works, but it's missing things a real product needs: password reset flows, email verification, MFA, protection against brute-force login attempts, secure token refresh, and a hosted login UI you don't have to build yourself. Building all of that correctly yourself is a genuinely hard, security-sensitive undertaking — this is exactly the kind of thing you should not reinvent in production. Cognito is AWS's managed identity service that does all of it.

What actually changes: Cognito replaces our users table + bcrypt + jsonwebtoken logic for authentication. Your users table in RDS doesn't disappear — it'll still store app-specific data (role, order history links), but the actual "who is this person / verify their password / issue a token" job moves to Cognito.

const jwt = require('jsonwebtoken');
const bcrypt = require('bcryptjs');
const pool = require('../config/db');

exports.register = async (req, res) => {
  const { name, email, password } = req.body;
  if (!name || !email || !password) {
    return res.status(400).json({ error: 'name, email and password are required' });
  }

  try {
    const [existing] = await pool.query('SELECT id FROM users WHERE email = ?', [email]);
    if (existing.length > 0) {
      return res.status(409).json({ error: 'User already exists' });
    }

    // Never store plaintext passwords - bcrypt one-way hashes with a random salt,
    // so even a full database leak doesn't expose usable passwords.
    const hashedPassword = await bcrypt.hash(password, 10);

    const [result] = await pool.query(
      'INSERT INTO users (name, email, password) VALUES (?, ?, ?)',
      [name, email, hashedPassword]
    );

    res.status(201).json({ message: 'User registered', userId: result.insertId });
  } catch (err) {
    console.error(err);
    res.status(500).json({ error: 'Registration failed' });
  }
};

exports.login = async (req, res) => {
  const { email, password } = req.body;
  try {
    const [rows] = await pool.query('SELECT * FROM users WHERE email = ?', [email]);
    if (rows.length === 0) {
      return res.status(401).json({ error: 'Invalid credentials' });
    }
    const user = rows[0];

    const match = await bcrypt.compare(password, user.password);
    if (!match) {
      return res.status(401).json({ error: 'Invalid credentials' });
    }

    const token = jwt.sign(
      { userId: user.id, email: user.email, role: user.role },
      process.env.JWT_SECRET || 'dev-secret-change-this',
      { expiresIn: '2h' }
    );

    res.json({ token });
  } catch (err) {
    console.error(err);
    res.status(500).json({ error: 'Login failed' });
  }
};

Phase 13: Email Notifications (SES + SNS)
Why this phase exists

Two different notification needs, two different services — worth understanding the distinction clearly:

SES (Simple Email Service): sends emails to customers — order confirmations, receipts, "your order shipped" — transactional emails tied to user actions.
SNS (Simple Notification Service): sends alerts to you/admins — "CPU is at 90%," "an EC2 instance failed a health check," "disk space low." It's for operational alerts, not customer-facing emails. We'll wire SNS properly into CloudWatch alarms in Phase 18; today we just set up the SNS topic and subscribe your email.

Cognito already handles verification emails (you just saw this working) — SES is specifically for your app's own transactional emails, like order confirmations, which Cognito has no concept of.

Phase 14: Background Processing (SQS + Lambda)
Why this phase exists

Right now, sending the order confirmation email happens inside the same request that creates the order — even though we made it non-blocking (fire-and-forget with .catch()), it's still running on your app server's resources, in the same process, competing with real user traffic. As your app grows, you'll want heavier background work — generating invoices, resizing uploaded product images, syncing inventory, sending batches of emails — done completely separately from your API servers.

This is what SQS (Simple Queue Service) + Lambda gives you: your API server's job becomes "drop a message in a queue and immediately respond to the user" — fast, decoupled. A separate Lambda function picks up messages from that queue and does the actual work, on its own schedule, with its own compute, retrying automatically if it fails.

Why not just call Lambda directly instead of using a queue? This is a genuinely important distinction:

Direct invoke: if Lambda is slow/down/throttled, your API request hangs or fails right there.
Via SQS: your API just writes to a queue (nearly instant, extremely reliable) and moves on. If Lambda is briefly unavailable, messages simply wait in the queue and get processed once it recovers — nothing is lost, nothing blocks the user. This is the standard decoupling pattern for anything that doesn't need to happen synchronously with the user's request.

Phase 15: HTTPS (ACM)
Why this phase exists

Right now your ALB serves plain http://. Every request — including login passwords and Cognito tokens — travels across the internet in plaintext. Anyone on the same network path (public wifi, compromised router, ISP-level snooping) can read it. HTTPS encrypts that traffic end-to-end using TLS. This isn't optional polish — it's a baseline requirement for anything handling auth or payments, and browsers increasingly flag plain HTTP sites as "Not Secure" outright.

ACM (AWS Certificate Manager) issues and auto-renews SSL/TLS certificates for free when used with AWS resources like ALB and CloudFront — no manual cert renewal, no Let's Encrypt cron jobs, no expired-cert outages at 3am.

Important dependency: ACM certificates for public websites need a domain name to issue against (it verifies you own the domain via DNS or email). Since Phase 16 (Route 53) is where we get a real domain, there's a slight ordering wrinkle — let's handle it correctly:

Q: Do you already own a domain name (from GoDaddy, Namecheap, Route 53, etc.) that you want to use for this project?
A: No I don't have but if it's free then I'll use it otherwise not

Being straight with you: there's no truly free domain option anymore. Freenom (which used to give away .tk/.ml/.ga domains) shut down in 2023 after abuse issues, and nothing legitimate has replaced it. Cheapest real options are things like .xyz or .site domains on Namecheap, often $1–3 for the first year (renews higher, ~$10-15/year after) — genuinely cheap, but not $0.

Since ACM can't issue a public certificate for the ALB's own *.elb.amazonaws.com address (you don't own that domain, AWS does — ACM verifies domain ownership, which is the whole point of a cert), HTTPS in any real/trusted sense requires a domain, no way around it.

Phase 16: Domain (Route 53)
Why this phase exists

Your domain is currently registered with name.com, but its DNS (which controls where yourdomain.com actually points) is separate from registration. We're going to point your domain's nameservers at Route 53 — AWS's DNS service — so that all the records (pointing to your ALB, verifying your SSL cert, etc.) live in the same place as the rest of your infrastructure, manageable via console/CLI like everything else.

Registrar vs DNS host — an important distinction: name.com stays your registrar (who you renew the domain through, who AWS/ICANN considers the legal owner-of-record). Route 53 becomes your DNS host (who answers "where does this domain point?"). These are commonly different companies, and that's completely normal — you're not transferring ownership, just changing who serves the DNS records.

Phase 17: CloudFront (CDN)
Why this phase exists

Back in Phase 11, we deliberately blocked all public access on the S3 image bucket and used short-lived pre-signed URLs instead — correct for security, but not great for actual product images that should just... load, instantly, for any visitor, without your backend generating a signed URL for every single image view. CloudFront solves this: it's a CDN (Content Delivery Network) that sits in front of S3, caches images at edge locations physically close to users worldwide, and serves them fast — while S3 itself stays completely private, never directly exposed.

How CloudFront reaches a "private" S3 bucket without making it public: CloudFront uses something called an Origin Access Control (OAC) — a special identity that only CloudFront can use to fetch objects from S3. You update the bucket policy to say "only this specific CloudFront distribution may read objects," and nothing else on the internet can. The bucket stays locked down exactly as configured in Phase 11; only the door CloudFront uses is opened, and only for reads.

The us-east-1 quirk I mentioned back in Phase 15: any ACM certificate used with CloudFront specifically (not ALB) must be requested in the us-east-1 (N. Virginia) region — a longstanding AWS architectural requirement, regardless of which region your actual resources live in. Since we want images.cloudcart.live (or similar) to also use HTTPS with your domain, we need a second ACM certificate, this one in us-east-1, even though everything else you've built is in ap-south-1.

Phase 19: CloudTrail
Why this phase exists

Everything we've done tonight — creating the VPC, launching instances, changing security groups, issuing certificates — AWS has been silently recording who did what, when, and from where the entire time, but by default that history isn't retained anywhere you can search later; it's only visible for ~90 days in a limited "Event history" view. CloudTrail turns this into a permanent, queryable audit log stored in S3.

Why this matters in practice, not just as a checkbox: if something ever goes wrong — a resource gets deleted by accident, a security group gets misconfigured, unexpected charges appear — CloudTrail is the first place any real ops/security team looks. It answers "who did this and when" definitively. It's also one of the first things auditors check for compliance (SOC2, ISO27001, etc.) in any company handling user data — which yours technically now does, given Cognito + RDS + real user records.

Let's connect some dots first, since you've been quietly using KMS all night without it being named: KMS (Key Management Service) is the encryption engine underneath almost every "Enable encryption" checkbox you've ticked tonight — RDS storage encryption (Phase 9), S3 default encryption (Phase 11, 19), CloudTrail log encryption (Phase 19). Phase 21: WAF + Shield
Why this phase exists

Every security group, Cognito auth, and parameterized SQL query we've built tonight protects against specific, known attack vectors — but none of it inspects the actual content of incoming HTTP requests for malicious patterns. WAF (Web Application Firewall) sits in front of your ALB and inspects every request before it reaches your app — blocking SQL injection attempts, cross-site scripting payloads, known bad bots, and requests from IPs with poor reputation, all without your app code ever having to think about it.

Shield is different and simpler to explain: Shield Standard is already protecting you right now, automatically, for free — it comes built into every AWS account and defends against common network/transport-layer DDoS attacks (SYN floods, UDP reflection, etc.) with zero setup. Shield Advanced is a paid tier ($3,000/month — genuinely enterprise pricing) with dedicated DDoS response support and cost protection guarantees; completely out of scope for a learning project, and worth knowing so you don't accidentally look for a button to enable something that costs three grand a month. What you should actually know for interviews: "Shield Standard is automatic and free; Shield Advanced is for large-scale production systems facing genuine targeted DDoS risk."

Why this phase exists

Your Docker image currently only exists on your laptop. ECR is a private, AWS-hosted registry — think of it as your own private Docker Hub, living inside your AWS account, with IAM controlling exactly who/what can push or pull images. Phase 24: ECS Fargate
Why this phase exists — the big shift

This phase replaces your entire EC2 + Auto Scaling Group + Launch Template + PM2 + Nginx setup with Fargate — AWS's serverless compute for containers. You stop managing servers entirely: no more patching OS packages, no more bootstrap scripts, no SSH/SSM into instances to debug — you just tell ECS "run this container image, with this much CPU/memory," and AWS handles literally everything underneath.

Core concepts, before we build:

Task Definition — a blueprint: which image, how much CPU/memory, which environment variables/secrets, which port. Think of it as the Fargate equivalent of your old Launch Template.
Task — one running instance of that blueprint (equivalent to one EC2 instance running your app).
Service — keeps a desired number of Tasks running, replaces failed ones automatically, and integrates with the ALB — equivalent to your old Auto Scaling Group.
Cluster — a logical grouping of services/tasks. With Fargate, a cluster doesn't correspond to physical servers you manage (unlike the old EC2-based ECS launch type) — it's purely an organizational container.

Phase 25: CI/CD (CodePipeline + CodeBuild + CodeDeploy)
Why this phase exists

Every single code change tonight has followed the same manual dance: push to GitHub, then manually docker build, docker tag, docker push, then manually update the ECS service. That's fine for learning, but it's slow and error-prone in practice — a forgotten step, a stale tag, a typo in a command, and you've deployed the wrong thing or nothing at all. CI/CD automates all of it: the moment you git push, a pipeline builds a fresh image, pushes it to ECR, and tells ECS to deploy it — consistently, the same way, every time.

The three pieces, and what each one actually does:

CodeBuild — runs your docker build + docker push commands in a managed, ephemeral build environment (you define the steps in a buildspec.yml, similar spirit to your bootstrap.sh but for the build process, not server setup)
CodePipeline — the orchestrator that watches GitHub, triggers CodeBuild when it sees a push, then triggers the ECS deployment step — the "glue" connecting everything
CodeDeploy — for ECS specifically, we'll actually use ECS's own built-in rolling deployment (simpler, and what most modern ECS setups actually use) rather than the separate CodeDeploy service, which is more commonly seen with EC2/Lambda deployments. Worth knowing that distinction for interviews — "ECS deployments" and "CodeDeploy" are related but not identical, and ECS's native rolling update is the more common real-world choice for container workloads.

Phase 26: Terraform (Core Infra)
Why this phase exists — the core concept before any code

Terraform works in 3 steps, always: write .tf files describing what you want to exist → terraform plan (shows you exactly what it will create/change/destroy, before touching anything — a dry run) → terraform apply (actually makes it happen). Terraform tracks everything it created in a state file — its memory of "what currently exists" — so next time you run apply, it only changes what's different, rather than recreating everything from scratch.

Important — we are NOT going to recreate your existing infrastructure with this. Your VPC/RDS/ALB/ECS are already running, built by hand tonight. Making Terraform "adopt" existing resources (called importing) is a genuinely more advanced, fiddly process — not the right use of time right now. Instead, we'll write Terraform config that describes an equivalent environment, which you'd use to spin up a second, independent copy (e.g., a staging environment) or rebuild from scratch if needed — while your current hand-built environment keeps running untouched. This is actually the more realistic beginner-safe way to learn Terraform anyway — zero risk to what's already live.
